# Documentation Technique : Plan d'Implémentation d'un Système RAG Avancé Style Cursor

## En-tête

*   **Titre** : Plan d'Implémentation : Système RAG Avancé Style Cursor
*   **Description concise** : Ce plan détaille la transformation progressive d'un système RAG existant en une architecture sophistiquée inspirée de Cursor. L'objectif est d'améliorer la qualité de récupération, les performances d'indexation et la compréhension structurelle du code grâce à l'implémentation du chunking sémantique (Tree-sitter), de la recherche hybride (FTS5 + vecteurs), de la synchronisation incrémentale (Merkle Tree) et d'un graphe de symboles.
*   **Dépendances** :
    *   `tree-sitter` (`>=0.20.0`)
    *   `tree-sitter-python` (`>=0.20.0`)
    *   `watchdog` (`>=3.0.0`)
    *   `networkx` (`>=3.0`)
    *   Potentiellement `priomptipy` (pour les améliorations avancées)

## Classes & Fonctions Prévues

Ce document décrit des composants planifiés plutôt que des implémentations existantes. Les signatures, arguments, retours et logiques internes sont basés sur les spécifications du plan.

### `features/context/code_chunker.py` (Nouveau module)

#### `class CodeChunker:` (Implicite)

Une classe ou un ensemble de fonctions utilitaires pour le découpage sémantique du code.

#### `chunk_file(file_path: str) -> List[Dict]`

*   **Description** : Découpe un fichier de code source en chunks sémantiques en utilisant Tree-sitter.
*   **Arguments** :
    *   `file_path` (`str`) : Le chemin complet vers le fichier source à chunker.
*   **Retours** : `List[Dict]`
    *   Une liste de dictionnaires, où chaque dictionnaire représente un chunk et contient :
        *   `content` (`str`) : Le contenu textuel du chunk.
        *   `ast_type` (`str`) : Le type AST du nœud (ex: 'function_definition', 'class_definition').
        *   `start_line` (`int`) : La ligne de début du chunk dans le fichier original.
        *   `end_line` (`int`) : La ligne de fin du chunk.
        *   `parent_context` (`str`) : Une chaîne de caractères décrivant le contexte parent (ex: "Fichier: X > Classe: Y > Méthode: Z").
*   **Logique interne** :
    1.  Utilise `tree-sitter-python` pour parser le fichier.
    2.  Applique des requêtes S-expressions pour extraire les définitions de classes et de fonctions.
    3.  Gère les "sticky headers" (inclusion de la signature de classe dans les méthodes qu'elle contient).
    4.  Implémente un algorithme de coalescence pour combiner de petits nœuds adjacents en des chunks plus significatifs.

#### `extract_dependencies(chunk: Dict) -> List[Dict]` (Modifier/Ajouter)

*   **Description** : Extrait les imports et les appels de fonctions d'un chunk de code donné.
*   **Arguments** :
    *   `chunk` (`Dict`) : Un dictionnaire représentant un chunk de code, tel que retourné par `chunk_file`.
*   **Retours** : `List[Dict]`
    *   Une liste de dictionnaires, où chaque dictionnaire contient des informations sur une dépendance (ex: type 'import' ou 'call', nom du module/fonction, ligne).
*   **Logique interne** :
    1.  Parse le contenu du chunk pour identifier les déclarations d'importation et les expressions d'appel de fonction.
    2.  Normalise les noms de symboles pour faciliter la construction du graphe.

### `features/context/database.py` (Modifié)

#### `index_project_files()` (Modification)

*   **Description** : Met à jour l'indexation des fichiers du projet.
*   **Logique interne** :
    1.  Utilise `CodeChunker.chunk_file()` pour le découpage sémantique.
    2.  Stocke les métadonnées AST (`ast_type`, `start_line`, `end_line`, `parent_context`) dans la table `knowledge`.
    3.  Les triggers SQL assurent la synchronisation automatique avec la table virtuelle FTS5 lors des insertions/mises à jour.
    4.  Dans la Phase 3, cette fonction sera modifiée pour utiliser `MerkleSync.sync_incremental()`.

#### `search_vector_db(query: str, top_k: int) -> List[Dict]` (Modification)

*   **Description** : Effectue une recherche hybride combinant la recherche vectorielle et la recherche plein texte (FTS5).
*   **Arguments** :
    *   `query` (`str`) : La requête de recherche de l'utilisateur.
    *   `top_k` (`int`) : Le nombre maximal de résultats à retourner.
*   **Retours** : `List[Dict]`
    *   Une liste de dictionnaires représentant les résultats fusionnés, chacun contenant le contenu du chunk, le chemin du fichier, le score de pertinence, etc.
*   **Logique interne** :
    1.  Exécute une recherche vectorielle (similitude cosinus avec les embeddings) sur l'index vectoriel (FAISS).
    2.  Exécute une recherche plein texte sur la table virtuelle FTS5.
    3.  Applique l'algorithme `reciprocal_rank_fusion()` pour combiner et reclasser les résultats des deux systèmes.

#### `reciprocal_rank_fusion(vector_results: List, fts_results: List, k: int = 60) -> List` (Nouveau/Ajout)

*   **Description** : Implémente l'algorithme Reciprocal Rank Fusion pour combiner des listes de résultats classées.
*   **Arguments** :
    *   `vector_results` (`List`) : Liste de résultats de la recherche vectorielle, classés par pertinence.
    *   `fts_results` (`List`) : Liste de résultats de la recherche plein texte, classés par pertinence.
    *   `k` (`int`, optionnel, défaut 60) : Paramètre de pondération pour la fusion des rangs.
*   **Retours** : `List`
    *   Une liste de résultats fusionnés, classés par le score RRF calculé.
*   **Logique interne** :
    1.  Attribue un score à chaque document en fonction de son rang dans chaque liste de résultats en utilisant la formule : `Score(d) = Σ(1 / (k + rank(d)))`.
    2.  Aggrège les scores pour les documents présents dans plusieurs listes.
    3.  Retourne la liste des documents, classée par leur score RRF total.

#### `sync_incremental()` (Nouveau)

*   **Description** : Déclenche une synchronisation incrémentale du projet, ré-indexant uniquement les fichiers modifiés.
*   **Logique interne** :
    1.  Utilise `MerkleTree.diff()` pour identifier les fichiers nouveaux, modifiés ou supprimés.
    2.  Pour les fichiers modifiés/nouveaux, appelle `CodeChunker.chunk_file()` et met à jour la base de données.
    3.  Met à jour les hachages SHA-256 et les timestamps dans la table `files`.

#### Schémas SQLite étendus

1.  **Table `knowledge`** :
    ```sql
    ALTER TABLE knowledge ADD COLUMN ast_type TEXT;
    ALTER TABLE knowledge ADD COLUMN start_line INTEGER;
    ALTER TABLE knowledge ADD COLUMN end_line INTEGER;
    ALTER TABLE knowledge ADD COLUMN parent_context TEXT;
    ```
2.  **Table virtuelle `fts_code`** :
    ```sql
    CREATE VIRTUAL TABLE fts_code USING fts5(
        content,
        path UNINDEXED,
        chunk_id UNINDEXED,
        tokenize='trigram'
    );
    ```
3.  **Table `files`** :
    ```sql
    CREATE TABLE files (
        id INTEGER PRIMARY KEY,
        path TEXT UNIQUE NOT NULL,
        checksum TEXT NOT NULL,
        last_indexed TIMESTAMP DEFAULT CURRENT_TIMESTAMP
    );
    ```

### `features/context/rag.py` (Modifié)

#### `handle_chat_rag_hybrid(query: str, chat_history: List[Dict]) -> str` (Modification)

*   **Description** : Gère une requête de chat en utilisant le système RAG hybride.
*   **Arguments** :
    *   `query` (`str`) : La question de l'utilisateur.
    *   `chat_history` (`List[Dict]`) : L'historique de la conversation.
*   **Retours** : `str`
    *   La réponse générée par le LLM, enrichie par le contexte RAG.
*   **Logique interne** :
    1.  Appelle `database.search_vector_db()` avec la requête pour obtenir des résultats hybrides.

    4.  Ajuste potentiellement les seuils de pertinence pour optimiser la qualité du contexte.

### `features/context/merkle_sync.py` (Nouveau module)

#### `class MerkleNode:`

*   **Description** : Représente un nœud dans l'arbre de Merkle.
*   **Attributs** :
    *   `hash` (`str`) : Le hachage SHA-256 du contenu (pour un fichier) ou la concaténation hachée des hachages enfants (pour un répertoire).
    *   `path` (`str`) : Le chemin relatif du fichier ou du répertoire.
    *   `is_file` (`bool`) : `True` si c'est un fichier, `False` si c'est un répertoire.
    *   `children` (`List[MerkleNode]`) : Liste des nœuds enfants pour un répertoire.

#### `class MerkleTree:` (Implicite)

Une classe pour gérer la construction et la comparaison des arbres de Merkle.

#### `build_tree(root_path: str) -> MerkleNode`

*   **Description** : Construit un arbre de Merkle pour le système de fichiers à partir d'un chemin racine.
*   **Arguments** :
    *   `root_path` (`str`) : Le chemin racine du dépôt ou du dossier à surveiller.
*   **Retours** : `MerkleNode`
    *   Le nœud racine de l'arbre de Merkle construit.
*   **Logique interne** :
    1.  Parcourt récursivement le système de fichiers à partir de `root_path`.
    2.  Pour chaque fichier, calcule son hachage SHA-256.
    3.  Pour chaque répertoire, calcule son hachage en combinant les hachages de ses enfants.

#### `diff(old_tree: MerkleNode, new_tree: MerkleNode) -> List[str]`

*   **Description** : Compare deux arbres de Merkle pour détecter les fichiers modifiés, ajoutés ou supprimés.
*   **Arguments** :
    *   `old_tree` (`MerkleNode`) : L'arbre de Merkle précédent.
    *   `new_tree` (`MerkleNode`) : Le nouvel arbre de Merkle.
*   **Retours** : `List[str]`
    *   Une liste des chemins des fichiers qui ont été modifiés (y compris ajoutés ou supprimés).
*   **Logique interne** :
    1.  Compare récursivement les hachages des nœuds.
    2.  Identifie les branches dont les hachages diffèrent, ce qui permet une détection O(log n) des changements.

### `features/context/file_watcher.py` (Nouveau module)

#### `class FileWatcher:` (Implicite)

Une classe pour surveiller les changements de fichiers en temps réel.

#### `start_watching(path: str, on_file_changed: Callable)`

*   **Description** : Démarre la surveillance d'un répertoire pour les modifications de fichiers.
*   **Arguments** :
    *   `path` (`str`) : Le chemin du répertoire à surveiller.
    *   `on_file_changed` (`Callable`) : Une fonction de callback à appeler lorsqu'un fichier est détecté comme "dirty".
*   **Logique interne** :
    1.  Utilise la bibliothèque `watchdog` pour détecter les événements de création, modification ou suppression de fichiers/répertoires.
    2.  Maintient une file d'attente interne pour les fichiers "dirty".
    3.  Utilise un thread d'arrière-plan pour traiter ces fichiers de manière asynchrone, appelant `on_file_changed` pour chaque fichier affecté.

### `features/context/symbol_graph.py` (Nouveau module)

#### `class SymbolGraph:`

*   **Description** : Gère la construction et l'analyse d'un graphe de symboles du projet.
*   **Attributs** :
    *   `graph` (`networkx.DiGraph`) : Le graphe orienté représentant les dépendances entre les fichiers et les symboles.
    *   `symbols` (`Dict[str, SymbolInfo]`) : Un mapping des noms de symboles vers leurs définitions (emplacement, type, etc.).

#### `build_graph(project_root_path: str)`

*   **Description** : Construit le graphe de symboles pour l'ensemble du projet.
*   **Arguments** :
    *   `project_root_path` (`str`) : Le chemin racine du projet.
*   **Logique interne** :
    1.  Parcourt tous les fichiers du projet.
    2.  Utilise `CodeChunker.extract_dependencies()` pour chaque chunk afin d'identifier les imports et les appels de fonctions.
    3.  Ajoute des nœuds au graphe pour les fichiers et les symboles (classes, fonctions).
    4.  Crée des arêtes dirigées pour représenter les dépendances (ex: "appelant -> appelé", "fichier_source -> fichier_importé").

#### `calculate_pagerank() -> Dict[str, float]`

*   **Description** : Calcule le score PageRank pour chaque nœud (fichier ou symbole) dans le graphe.
*   **Retours** : `Dict[str, float]`
    *   Un dictionnaire mappant les noms de fichiers/symboles à leurs scores PageRank.
*   **Logique interne** :
    1.  Appelle la fonction `networkx.pagerank()` sur le graphe interne.
    2.  Le PageRank est utilisé pour identifier les fichiers ou symboles les plus centraux et influents du projet.

### `features/context/repo_map.py` (Nouveau module)

#### `class RepoMapGenerator:` (Implicite)

Une classe pour générer une carte compressée du dépôt.

#### `generate_repo_map(symbol_graph: SymbolGraph, top_n_files: int) -> str`

*   **Description** : Génère une représentation textuelle compacte (carte du dépôt) des éléments clés du projet.
*   **Arguments** :
    *   `symbol_graph` (`SymbolGraph`) : L'instance du graphe de symboles du projet.
    *   `top_n_files` (`int`) : Le nombre de fichiers les plus importants (selon PageRank) à inclure.
*   **Retours** : `str`
    *   Une chaîne de caractères représentant la carte du dépôt, optimisée pour être injectée dans un LLM.
*   **Logique interne** :
    1.  Utilise `symbol_graph.calculate_pagerank()` pour obtenir les scores d'importance des fichiers.
    2.  Sélectionne les `top_n_files` les plus pertinents.
    3.  Pour chacun de ces fichiers, extrait uniquement les signatures des classes et fonctions (sans le corps d'implémentation).
    4.  Formate ces signatures dans une structure textuelle hiérarchique et compacte.

## Exemple d'Usage (Workflow Cible)

Cet exemple décrit un scénario d'interaction typique avec le système RAG avancé, illustrant l'intégration des différentes phases.

```python
# Pseudo-code illustratif du workflow

from features.context.code_chunker import CodeChunker
from features.context.database import (
    initialize_db, index_project_files, search_vector_db, sync_incremental
)
from features.context.file_watcher import FileWatcher
from features.context.symbol_graph import SymbolGraph
from features.context.repo_map import RepoMapGenerator
from features.context.rag import handle_chat_rag_hybrid

# --- Initialisation et Indexation Initiale ---
project_root = "/path/to/my/project"
initialize_db()

# La première indexation utilise le chunking sémantique
# et construit le graphe de symboles.
print("Démarrage de l'indexation initiale...")
# La fonction index_project_files() aura été modifiée pour appeler CodeChunker
# et potentiellement initier la construction du graphe de symboles.
index_project_files(project_root)
print("Indexation initiale terminée.")

# --- Surveillance en Temps Réel ---
def on_file_dirty(file_path: str):
    print(f"Fichier modifié détecté: {file_path}. Synchronisation incrémentale...")
    sync_incremental(file_path) # sync_incremental sera appelé pour ré-indexer le fichier spécifique
    print(f"Synchronisation de {file_path} terminée.")

watcher = FileWatcher()
# Le file watcher notifiera lorsqu'un fichier est modifié, déclenchant sync_incremental
watcher.start_watching(project_root, on_file_dirty) 
print(f"Surveillance des fichiers démarrée pour {project_root}...")

# --- Préparation du Contexte Avancé ---
# Le graphe de symboles est construit en arrière-plan ou mis à jour après chaque indexation
symbol_graph_instance = SymbolGraph()
symbol_graph_instance.build_graph(project_root)
symbol_graph_instance.calculate_pagerank()

# Génération de la carte du dépôt pour un contexte global
repo_map_content = RepoMapGenerator().generate_repo_map(symbol_graph_instance, top_n_files=5)
print("\n--- Carte du dépôt générée ---")
print(repo_map_content)
print("-----------------------------\n")

# --- Interaction RAG Hybride ---
user_query = "Comment la fonction 'process_data' dans 'src/data_processor.py' interagit-elle avec le module de base de données?"
chat_history = [] # ou une liste de messages précédents

print(f"Requête utilisateur: {user_query}")

# handle_chat_rag_hybrid utilisera la recherche hybride (FTS5 + vecteurs)
# et pourra intégrer la repo_map ou le graphe de symboles pour un contexte plus riche.
llm_response = handle_chat_rag_hybrid(user_query, chat_history, repo_map=repo_map_content)

print("\nRéponse du LLM (avec RAG hybride et contexte):")
print(llm_response)

# (En arrêtant le programme, on arrêterait aussi le watcher)
# watcher.stop_watching()
