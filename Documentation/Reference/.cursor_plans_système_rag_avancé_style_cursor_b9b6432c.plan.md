# Documentation Technique : Système RAG Avancé Style Cursor

## En-tête

*   **Titre** : Système RAG Avancé Style Cursor
*   **Description concise** : Implémentation progressive d'un système RAG avancé inspiré de Cursor, remplaçant les composants existants par des solutions plus performantes pour le chunking sémantique, la recherche hybride, la synchronisation incrémentale, et l'intégration d'un graphe de symboles. L'objectif est d'améliorer significativement la qualité et la pertinence du contexte fourni aux modèles de langage.
*   **Dépendances** :
    *   `tree-sitter>=0.20.0`
    *   `tree-sitter-python>=0.20.0`
    *   `watchdog>=3.0.0`
    *   `networkx>=3.0`
    *   `sentence-transformers>=2.2.0` (pour le reranking)
    *   `faiss-cpu` (pour l'index FAISS)
    *   `sqlite3` (intégré à Python, pour la base de données et FTS5)
    *   *Optionnel* : `multilspy` (pour Shadow Workspace), `priomptipy` (pour gestion contexte)

## Classes & Fonctions

### 1. Phase 1 : Chunking Sémantique avec Tree-sitter

**Fichier** : `features/context/tree_sitter_chunker.py`

*   **Classe** : `SemanticChunker`
    *   **Description** : Fournit des méthodes pour découper le code source en "chunks" sémantiquement cohérents en utilisant l'analyse syntaxique (AST) fournie par Tree-sitter.
    *   **Méthodes** :
        *   `__init__(self, language: str)`
            *   **Arguments** :
                *   `language` (str) : Le langage de programmation à analyser (ex: "python", "javascript").
            *   **Logique interne** : Initialise le parser Tree-sitter pour le langage spécifié et charge sa grammaire.
        *   `chunk_code(self, code: str, file_path: str) -> List[Dict]`
            *   **Arguments** :
                *   `code` (str) : Le contenu du fichier de code source.
                *   `file_path` (str) : Le chemin relatif ou absolu du fichier.
            *   **Retours** : `List[Dict]` - Une liste de dictionnaires, où chaque dictionnaire représente un chunk et contient au moins `{ "content": str, "path": str, "start_line": int, "end_line": int, "id": str, "parent_context": str }`.
            *   **Logique interne** :
                1.  Parse le `code` en utilisant Tree-sitter pour obtenir l'Arbre Syntaxique Abstrait (AST).
                2.  Traverse l'AST pour identifier les nœuds de définition principaux (classes, fonctions, méthodes).
                3.  Applique une stratégie "Coarse-to-Fine" : D'abord les grandes structures (classes), puis les sous-structures (méthodes).
                4.  Pour chaque nœud extrait, génère un chunk de texte correspondant.
                5.  Ajoute un "Sticky Header" ou "Contexte Parent" (ex: `Fichier: X > Classe: Y > Méthode: Z`) à chaque chunk pour préserver le contexte hiérarchique.
                6.  Gère les "code orphelin" (code qui n'appartient pas à une définition majeure) en le chunkant par paragraphes ou en le rattachant au chunk précédent/suivant pertinent.
                7.  Génère un identifiant unique (`id`) pour chaque chunk.

**Fichier** : `features/context/database.py` (modifié)

*   **Fonction** : `index_project_files(project_path: str, chunker: SemanticChunker)`
    *   **Arguments** :
        *   `project_path` (str) : Chemin vers la racine du projet à indexer.
        *   `chunker` (SemanticChunker) : Une instance du chunker sémantique à utiliser.
    *   **Logique interne** : Iteère sur les fichiers du projet, lit leur contenu, utilise `chunker.chunk_code()` pour obtenir les chunks, calcule les embeddings de chaque chunk, et les stocke dans la base de données (SQLite/FAISS).

**Fichier** : `features/context/rag.py` (modifié)

*   **Fonction** : `chunk_text(text: str, file_path: str, chunker: SemanticChunker) -> List[Dict]`
    *   **Arguments** : Identiques à `SemanticChunker.chunk_code`.
    *   **Logique interne** : Agit comme un wrapper, déléguant l'appel à `chunker.chunk_code()`.

### 2. Phase 2 : Recherche Hybride (Dense + Sparse)

**Fichier** : `features/context/database.py` (modifié)

*   **Fonction** : `create_fts_table(db_conn)`
    *   **Arguments** :
        *   `db_conn` : Connexion à la base de données SQLite.
    *   **Logique interne** : Exécute une requête SQL pour créer une table virtuelle `fts_code` utilisant FTS5 avec le tokenizer 'trigram' pour une recherche lexicale efficace.
        ```sql
        CREATE VIRTUAL TABLE fts_code USING fts5(
            content, path UNINDEXED, chunk_id UNINDEXED, tokenize='trigram'
        );
        ```
*   **Fonction** : `add_chunk_to_fts(db_conn, chunk: Dict)`
    *   **Arguments** :
        *   `db_conn` : Connexion à la base de données SQLite.
        *   `chunk` (Dict) : Un dictionnaire représentant un chunk avec `content`, `path`, `chunk_id`.
    *   **Logique interne** : Insère ou met à jour le `content` du chunk dans la table `fts_code`, en le liant à son `chunk_id` et `path`.
*   **Fonction** : `search_hybrid(query: str, top_k: int = 10) -> List[Dict]`
    *   **Arguments** :
        *   `query` (str) : La requête de l'utilisateur.
        *   `top_k` (int) : Le nombre maximum de résultats à retourner.
    *   **Retours** : `List[Dict]` - Une liste de dictionnaires représentant les chunks les plus pertinents, triés par score RRF.
    *   **Logique interne** :
        1.  **Recherche Dense (Vectorielle)** : Convertit la `query` en embedding, puis effectue une recherche de similarité vectorielle dans l'index FAISS pour obtenir les `N` chunks les plus proches sémantiquement.
        2.  **Recherche Sparse (Lexicale)** : Effectue une recherche plein texte de la `query` dans la table FTS5 (BM25) pour obtenir les `N` chunks les plus proches lexicalement.
        3.  **Fusion RRF (Reciprocal Rank Fusion)** : Combine les résultats des deux recherches en utilisant l'algorithme RRF pour produire un classement unique et robuste. Pour chaque document `d` et pour chaque liste de résultats où il apparaît, son score RRF est calculé comme `Σ 1 / (k + rank(d))`, où `k` est une constante (souvent 60).
        4.  Récupère le contenu complet des `top_k` chunks fusionnés depuis la base de données principale et les retourne.

**Fichier** : `features/context/rag.py` (modifié)

*   **Fonction** : `get_context(query: str, project_id: str, k: int) -> List[str]`
    *   **Logique interne** : Met à jour pour appeler `features.context.database.search_hybrid()` au lieu de la recherche vectorielle seule.

### 3. Phase 3 : Synchronisation Incrémentale avec Merkle Tree

**Fichier** : `features/context/merkle_sync.py`

*   **Classe** : `MerkleTree`
    *   **Description** : Implémente un arbre de Merkle pour détecter efficacement les changements dans un répertoire de fichiers.
    *   **Méthodes** :
        *   `__init__(self, root_dir: str)`
            *   **Arguments** :
                *   `root_dir` (str) : Le répertoire racine à surveiller.
            *   **Logique interne** : Initialise le chemin racine.
        *   `_hash_file(self, file_path: str) -> str`
            *   **Logique interne** : Calcule le hachage SHA-256 du contenu d'un fichier.
        *   `_hash_dir(self, dir_path: str, children_hashes: List[str]) -> str`
            *   **Logique interne** : Calcule le hachage d'un répertoire en combinant et hachant les hachages de ses enfants (fichiers et sous-répertoires).
        *   `build_tree(self) -> Dict[str, str]`
            *   **Retours** : `Dict[str, str]` - Un dictionnaire mappant les chemins aux hachages, incluant le hachage racine sous une clé spécifique (ex: "ROOT").
            *   **Logique interne** : Traverse le `root_dir` de manière récursive, calcule les hachages des fichiers (feuilles), puis agrège ces hachages pour former les hachages des répertoires (nœuds) jusqu'à obtenir le hachage racine de l'arbre.
        *   `get_diff(self, old_merkle_state: Dict[str, str]) -> List[str]`
            *   **Arguments** :
                *   `old_merkle_state` (Dict[str, str]) : L'état précédent de l'arbre de Merkle (chemins -> hachages).
            *   **Retours** : `List[str]` - Une liste des chemins de fichiers qui ont été modifiés, ajoutés ou supprimés.
            *   **Logique interne** : Compare le hachage racine actuel avec `old_merkle_state`. Si différents, traverse l'arbre de manière hiérarchique (de O(N) à O(k log N) où k est le nombre de changements) pour identifier les fichiers exacts qui ont changé.

**Fichier** : `features/context/file_watcher.py`

*   **Classe** : `FileWatcher` (hérite de `watchdog.events.FileSystemEventHandler`)
    *   **Description** : Utilise la bibliothèque `watchdog` pour surveiller les modifications du système de fichiers en temps réel.
    *   **Méthodes** :
        *   `__init__(self, project_path: str, dirty_files_queue: Queue)`
            *   **Arguments** :
                *   `project_path` (str) : Le chemin du projet à surveiller.
                *   `dirty_files_queue` (Queue) : Une file d'attente pour ajouter les chemins des fichiers modifiés.
            *   **Logique interne** : Initialise l'observateur `watchdog` et la file d'attente.
        *   `start(self)`
            *   **Logique interne** : Démarre l'observateur de `watchdog` dans un thread séparé.
        *   `stop(self)`
            *   **Logique interne** : Arrête l'observateur.
        *   `on_modified(self, event)`
            *   **Arguments** :
                *   `event` (watchdog.events.FileSystemEvent) : L'événement de modification du système de fichiers.
            *   **Logique interne** : Surchargée pour intercepter les événements de modification de fichiers et de répertoires. Ajoute le chemin du fichier (`event.src_path`) à `dirty_files_queue` s'il s'agit d'un fichier et non d'un répertoire.
        *   `on_created(self, event)`, `on_deleted(self, event)`, `on_moved(self, event)`
            *   **Logique interne** : Similaires à `on_modified`, ajoutent les fichiers affectés à la file d'attente.

**Fichier** : `features/context/database.py` (modifié)

*   **Fonction** : `get_merkle_root(db_conn) -> Optional[str]`
    *   **Logique interne** : Récupère le hachage racine Merkle stocké de la base de données.
*   **Fonction** : `update_merkle_root(db_conn, new_root_hash: str)`
    *   **Logique interne** : Met à jour le hachage racine Merkle dans la base de données.
*   **Fonction** : `process_dirty_files(db_conn, merkle_tree: MerkleTree, dirty_files_queue: Queue)`
    *   **Logique interne** : Un thread ou un processus en arrière-plan qui :
        1.  Récupère périodiquement les fichiers de `dirty_files_queue`.
        2.  Calcule le nouvel arbre Merkle (`merkle_tree.build_tree()`).
        3.  Compare avec l'ancien état (`merkle_tree.get_diff()`) pour confirmer les modifications.
        4.  Pour chaque fichier modifié/ajouté/supprimé, déclenche la ré-indexation ou la suppression des chunks correspondants dans SQLite et FAISS, et met à jour FTS5.
        5.  Met à jour le hachage racine Merkle dans la base de données (`update_merkle_root()`).

### 4. Phase 4 : Graphe de Symboles et Repo Map

**Fichier** : `features/context/symbol_graph.py`

*   **Classe** : `SymbolGraph`
    *   **Description** : Construit et gère un graphe des symboles du code source (classes, fonctions, imports) et de leurs relations.
    *   **Méthodes** :
        *   `__init__(self)`
            *   **Logique interne** : Initialise une instance de `networkx.DiGraph`.
        *   `extract_symbols_and_relations(self, code: str, file_path: str, language: str)`
            *   **Arguments** :
                *   `code` (str) : Contenu du fichier.
                *   `file_path` (str) : Chemin du fichier.
                *   `language` (str) : Langage de programmation.
            *   **Retours** : `List[Dict]` - Liste de relations découvertes (`{"source": str, "target": str, "type": str}`).
            *   **Logique interne** :
                1.  Utilise Tree-sitter pour parser le code.
                2.  Parcourt l'AST pour identifier les définitions (classes, fonctions) et les références (appels de fonctions, imports).
                3.  Ajoute des nœuds au graphe pour chaque symbole (avec des attributs comme type, portée, ligne).
                4.  Ajoute des arêtes au graphe pour modéliser les relations (ex: "appelle", "importe", "définit", "hérite de").
        *   `build_graph_from_project(self, project_path: str)`
            *   **Logique interne** : Itère sur tous les fichiers du projet, appelle `extract_symbols_and_relations` pour chacun, et peuple le graphe.
        *   `calculate_pagerank(self) -> Dict[str, float]`
            *   **Retours** : `Dict[str, float]` - Un dictionnaire mappant les nœuds (symboles ou chemins de fichiers) à leurs scores PageRank.
            *   **Logique interne** : Appelle `networkx.pagerank()` sur le graphe construit pour identifier les symboles ou fichiers les plus "importants" ou centraux.
        *   `get_related_symbols(self, symbol_name: str, relation_type: Optional[str] = None) -> List[str]`
            *   **Logique interne** : Récupère les symboles connectés à un symbole donné par une arête de type spécifique.

**Fichier** : `features/context/repo_map.py`

*   **Classe** : `RepoMapGenerator`
    *   **Description** : Génère une carte de haut niveau du dépôt, résumant la structure et les APIs des fichiers importants.
    *   **Méthodes** :
        *   `generate_repo_map(self, symbol_graph: SymbolGraph, top_n_files: int = 5) -> str`
            *   **Arguments** :
                *   `symbol_graph` (SymbolGraph) : Une instance du graphe de symboles déjà construite.
                *   `top_n_files` (int) : Nombre de fichiers à haut PageRank à inclure dans la carte.
            *   **Retours** : `str` - Une chaîne de caractères représentant la carte du dépôt.
            *   **Logique interne** :
                1.  Utilise `symbol_graph.calculate_pagerank()` pour identifier les fichiers et symboles les plus importants.
                2.  Sélectionne les `top_n_files` à haut PageRank.
                3.  Pour chaque fichier sélectionné, extrait les signatures de ses classes et fonctions (sans le corps des méthodes) en utilisant l'AST pour créer un "squelette" de l'API interne.
                4.  Assemble ces squelettes dans une représentation textuelle concise et formatée.

**Fichier** : `features/context/database.py` (modifié)

*   **Fonction** : `store_symbol_relations(db_conn, relations: List[Dict])`
    *   **Logique interne** : Persiste les relations extraites par `SymbolGraph` dans une table SQLite dédiée (ex: `symbol_relations(source TEXT, target TEXT, type TEXT, file_path TEXT)`).

### 5. Phase 5 : Reranking

**Fichier** : `features/context/reranker.py`

*   **Classe** : `Reranker`
    *   **Description** : Utilise un modèle de "cross-encoder" pour affiner le classement des documents récupérés par la recherche hybride.
    *   **Méthodes** :
        *   `__init__(self, model_name: str = "bge-reranker-v2-m3")`
            *   **Arguments** :
                *   `model_name` (str) : Le nom du modèle de reranking à charger (ex: "bge-reranker-v2-m3", "mixedbread-ai/mxbai-rerank").
            *   **Logique interne** : Charge le modèle de reranking (généralement basé sur `sentence-transformers`).
        *   `rerank(self, query: str, documents: List[str]) -> List[Dict]`
            *   **Arguments** :
                *   `query` (str) : La requête originale de l'utilisateur.
                *   `documents` (List[str]) : Une liste de chaînes de caractères représentant les documents (chunks) à reranker, souvent les top-K résultats de la recherche hybride.
            *   **Retours** : `List[Dict]` - Une liste de dictionnaires, chaque dict contenant le `content` du document et son `score` reranké, triés par score décroissant.
            *   **Logique interne** :
                1.  Formate les paires `(query, document)` pour le modèle de reranking.
                2.  Passe ces paires au modèle pour obtenir des scores de pertinence.
                3.  Trie les documents en fonction de ces nouveaux scores.

**Fichier** : `features/context/database.py` (modifié)

*   **Fonction** : `search_hybrid(query: str, top_k: int = 10, reranker: Optional[Reranker] = None) -> List[Dict]`
    *   **Logique interne** : Intègre le reranking. Après la fusion RRF, si un `reranker` est fourni, il sera appliqué aux résultats préliminaires avant le retour final.

### 6. Phase 6 : Shadow Workspace / Validation LSP (Avancé)

**Fichier** : `features/context/shadow_workspace.py`

*   **Classe** : `ShadowWorkspace`
    *   **Description** : Crée et gère un environnement de travail virtuel pour tester et valider des modifications de code proposées, en utilisant les capacités d'un serveur LSP.
    *   **Méthodes** :
        *   `__init__(self, project_path: str, lsp_server_config: Dict)`
            *   **Arguments** :
                *   `project_path` (str) : Le chemin du projet principal.
                *   `lsp_server_config` (Dict) : Configuration pour le serveur LSP (ex: chemin de l'exécutable, arguments).
            *   **Logique interne** : Crée un répertoire temporaire pour le workspace virtuel, initialise `multilspy` et démarre le serveur LSP.
        *   `apply_changes(self, file_path: str, new_content: str)`
            *   **Arguments** :
                *   `file_path` (str) : Chemin du fichier dans le workspace virtuel.
                *   `new_content` (str) : Le nouveau contenu à écrire dans le fichier.
            *   **Logique interne** : Écrit le `new_content` dans le fichier spécifié dans le workspace virtuel et notifie le serveur LSP de la modification.
        *   `get_diagnostics(self, file_path: str) -> List[Dict]`
            *   **Arguments** :
                *   `file_path` (str) : Chemin du fichier à analyser.
            *   **Retours** : `List[Dict]` - Une liste de dictionnaires représentant les diagnostics (erreurs, avertissements) du LSP.
            *   **Logique interne** : Interroge le serveur LSP via `multilspy` pour obtenir les diagnostics du fichier.
        *   `auto_correct(self, file_path: str) -> Optional[str]`
            *   **Logique interne** : (Avancé) Utilise les capacités de correction automatique du LSP ou un modèle LLM pour tenter de corriger les erreurs détectées, et retourne le contenu corrigé.
        *   `cleanup(self)`
            *   **Logique interne** : Arrête le serveur LSP et supprime le répertoire temporaire.

### 7. Phase 7 : Gestion de Contexte avec PriomptiPy (Avancé)

**Fichier** : `features/context/context_manager.py`

*   **Classe** : `ContextManager`
    *   **Description** : Gère la composition du prompt final pour le LLM en respectant un budget de tokens et en priorisant les différents éléments contextuels.
    *   **Méthodes** :
        *   `__init__(self, max_tokens: int)`
            *   **Arguments** :
                *   `max_tokens` (int) : Le budget maximum de tokens pour le prompt.
            *   **Logique interne** : Initialise le gestionnaire de contexte avec le budget et une structure pour stocker les éléments.
        *   `add_element(self, content: str, priority: int, element_type: str, metadata: Optional[Dict] = None)`
            *   **Arguments** :
                *   `content` (str) : Le texte de l'élément à ajouter.
                *   `priority` (int) : Une valeur numérique indiquant la priorité (plus élevé = plus important).
                *   `element_type` (str) : Le type d'élément (ex: "system_instruction", "active_file", "rag_snippet", "error_log").
                *   `metadata` (Optional[Dict]) : Métadonnées associées à l'élément (ex: chemin du fichier, lignes).
            *   **Logique interne** : Ajoute l'élément à une liste interne, en stockant son contenu, sa priorité et son type.
        *   `compose_prompt(self, llm_tokenizer: Any) -> str`
            *   **Arguments** :
                *   `llm_tokenizer` (Any) : Le tokenizer du modèle de langage (ex: `tiktoken`) pour estimer le nombre de tokens.
            *   **Retours** : `str` - Le prompt final composé.
            *   **Logique interne** :
                1.  Trie tous les éléments ajoutés par `priority` décroissante.
                2.  Itère sur les éléments triés, en les ajoutant au prompt tant que le `max_tokens` n'est pas dépassé.
                3.  Utilise `llm_tokenizer` pour estimer le nombre de tokens de chaque élément et du prompt en cours de construction.
                4.  Si un élément est trop grand, il peut être tronqué ou omis en fonction de stratégies définies.
                5.  Assemble les éléments choisis dans une structure de prompt cohérente.

        # Simule des résultats de FTS5
        # Retourne une liste de (score, chunk_id)
        self.cursor.execute("SELECT chunk_id FROM fts_code WHERE content MATCH ? ORDER BY rank", (query + "*",))

        sparse_results = self.search_fts5(query, top_k * 2)

        # Implémentation simplifiée de RRF (Reciprocal Rank Fusion)
        rank_scores = {}
        k_rrf = 60 # Constante pour RRF

        for rank, (score, chunk_id) in enumerate(dense_results):
            rank_scores[chunk_id] = rank_scores.get(chunk_id, 0.0) + 1.0 / (k_rrf + rank + 1)

        for rank, (score, chunk_id) in enumerate(sparse_results):
            rank_scores[chunk_id] = rank_scores.get(chunk_id, 0.0) + 1.0 / (k_rrf + rank + 1)

        # Trier les chunks par score RRF et récupérer leur contenu
        sorted_chunk_ids = sorted(rank_scores.keys(), key=lambda id: rank_scores[id], reverse=True)[:top_k]
        
        results = [self.get_chunk_by_id(cid) for cid in sorted_chunk_ids]
        return [r for r in results if r is not None]
